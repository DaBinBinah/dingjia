# 《盯价》踩坑复盘与开发防护规范（Lessons Learned）

> **目的**：将实际开发与生产排查中遇到的真实故障、数据冲突与隐蔽 Bug 进行第一性原理复盘，沉淀为永久性的工程规范，防止后续开发中再次发生同样的错误。

---

## 📌 案例 1：新增标的提示“暂无行情”（2026-08-31）

### 1. 现象描述
用户在非交易时段（如晚上、周末）在前端点击“＋添加监控”录入了 `600797`（浙大网新）和 `600841`（动力新科），添加成功后列表卡片始终显示“暂无行情”，行情时间为“—”，价格线显示“待行情”。

### 2. 根因剖析（两条链路叠加）
- **根因 A（写操作未同步初始快照）**：
  `ths-create-watch` 云函数在将新标的写入 `ths_watchlist` 时，将 `currentPrice`、`changePercent` 简单初始化为 `null`，并假设“后续依赖定时任务 `ths-check-market` 去异步拉取”。
  然而在**非交易时段**，`ths-check-market` 会自动跳过扫描（节流降耗），导致新标的的行情字段一直为 `null`，产生系统失效的错觉。
- **根因 B（定时云函数内部未定义变量 ReferenceError）**：
  在 `ths-check-market` 内部重构跨日判断时，使用了 `lastDate !== today`，但 `today` 变量未在 `exports.main` 作用域声明，导致手动触发（`force=true`）在遍历第一条标的时直接崩溃抛错，未能执行更新。

### 3. 防护与开发铁律
1. **【铁律：添加即所得】**：
   任何新建标的（单个添加 `ths-create-watch`、批量导入 `ths-import-watches`、添加持仓 `ths-create-holding`）在插入数据库前，**服务端必须主动调用一次行情接口 `fetchQuotes`**，将最新收盘价/实时价格、涨跌幅、时间戳一并写入初始文档。
2. **【铁律：作用域变量严密性与本地验证】**：
   所有时间与上下文变量（如 `startedAt`、`today`、`phase`、`nowMs`）必须在函数入口处统一完成初始化。部署前必须在本地使用 Node.js 模拟调用一次，防止任何 `ReferenceError`。
3. **【铁律：前端异常显性化】**：
   前端异步请求的 `catch` 块严禁使用 `catch (_)` 盲吞错误。所有数据操作失败必须弹出友好 Toast 或在控制台记录错误，便于第一时间定位。

## 📌 案例 2：512720 计算机ETF 实时价格与历史日 K 冲突（2026-08-31）

### 1. 现象描述
盘中实时行情显示为 `¥1.204 (+2.73%)`，但历史日 K 表格的最后一行却显示当天收盘价为早盘的 `1.166`，两者存在明显数据矛盾。

### 2. 根因剖析
历史行情接口直接将当天盘中未收盘的临时 K 线当作“已完成的历史日线”写入了历史表格。盘中价格瞬息万变，盘中临时行情绝不能作为“历史收盘价”展示。

### 3. 防护与开发铁律
1. **【铁律：盘中与历史严格分离】**：
   - 处于**盘中交易时间**（`pre_market`、`trading_morning`、`trading_afternoon`、`midday_break`）时，历史行情最后一条**只能是上一个已完成交易日**，当天数据仅在实时行情区展示；
   - 处于**已收盘**（`closed`）后，历史行情的最后一条必须使用当天的**最终收盘价**，确保与实时价格 100% 严格一致。

## 📌 案例 3：近 20 日涨跌统计“9+9=18”天数缺失（2026-08-31）

### 1. 现象描述
近 20 日行情统计中，卡片仅展示了 `9次上涨 ｜ 9次下跌`，相加仅 18 天，丢失了 2 天。

### 2. 根因剖析
前端仅对 `pct > 0` 和 `pct < 0` 做了统计，忽略了 `pct === 0` 的持平天数。在 20 个交易日中，若有 2 天持平，就会出现 9+9=18 的视觉假象。

### 3. 防护与开发铁律
1. **【铁律：区间统计完整性】**：
   所有基于日线的统计计算，必须完整覆盖全集：`总天数 = 上涨天数 + 下跌天数 + 持平天数`。前端渲染必须三者同时展示（如 `10 上涨 ｜ 8 下跌 ｜ 2 持平 = 20 天`），严禁遗漏任何边界分支。

## 📌 案例 4：ETF 无分红方案时误显示为 0% 或 0 元（2026-08-31）

### 1. 现象描述
某些暂未公布收益分配方案的 ETF，在分红雷达或详情页中被格式化为 `股息率 0.00%` 或 `每份分红 ¥0.00`。

### 2. 根因剖析
后端未区分“数据不存在（null）”与“分红为零（0）”，将空值盲目转换为 0 输出给前端，导致误导用户以为该基金有分红方案但分红为 0。

### 3. 防护与开发铁律
1. **【铁律：真实数据与纯净隐藏】**：
   严守“无方案即隐藏”原则。如果标的（尤其是 ETF）在官方数据源中未查询到有效分红决议，字段必须保持 `null`，前端直接对分红雷达和股息率区域进行纯净隐藏，绝不可显示虚假的 0.00% 或 ¥0.00。

## 📌 案例 5：多项目同环境静态托管与数据库隔离（2026-08-31）

### 1. 现象描述
同一 CloudBase 环境 `REDACTED_CLOUDBASE_ENV_ID` 中同时运行着【亲子艺术】（根路径 `/`）与【盯价】（子路径 `/ths/`）。

### 2. 潜在风险
若部署命令写错为 `npx tcb hosting deploy ./web`（未指定目标子路径 `ths`），会导致根目录下的【亲子艺术】项目被直接覆盖损坏！

### 3. 防护与开发铁律
1. **【铁律：静态托管独占子路径】**：
   部署命令必须且只能是：`npx tcb hosting deploy ./web ths -e REDACTED_CLOUDBASE_ENV_ID`。严禁省略子路径 `ths`。
2. **【铁律：数据库集合统一前缀】**：
   盯价项目的所有数据库集合一律以 `ths_*` 命名（如 `ths_watchlist`、`ths_holdings`、`ths_price_touches` 等），严禁读写或修改非 `ths_` 开头的任何外部集合。

## 📌 案例 6：财务指标探测顺序与云端日度缓存（2026-08-31）

### 1. 现象描述
股票详情页新增【公司基本面】后，用户打开页面时提示“暂无数据”或长时间处于占位状态。

### 2. 根因剖析
1. **财报期正向探测导致连续 404**：云函数在查询上市公司 ROE 时，按未发布的远期财报（如 `2026-4`、`2026-3`、`2026-2`...）向后倒推，导致每次请求都要经历 4~6 次 404/5003 错误重试，耗时达 3~5 秒触发前端异步超时；
2. **缺少云端缓存**：上市公司基本面指标（PE、PB、ROE）变动频率极低（日度/季度），直接高频穿透打到底层 API 造成响应慢与配额浪费。

### 3. 防护与开发铁律
1. **【铁律：财报探测优先命中已发布最新年报】**：
   针对财务指标查询，优先探测 `2024-4`（最新完整年报）、`2024-3`（三季报）、`2024-2`（中报），将接口耗时从 3000ms+ 压缩至 160ms；
2. **【铁律：低频指标引入云端数据库日度缓存】**：
   对 PE、PB、ROE 等低频数据，首次查询后写入 `ths_history_cache` 集合（12小时有效），同一天内二次查询直接从缓存读取，实现 49ms 极速秒开。

## 📌 案例 7：Serverless 触发器与用户刷新并发竞争导致重复提醒（2026-09-03）

### 1. 现象描述
在标的触达买入价时，用户手机微信连续收到两条完全相同的推送模板消息，数据库 `ths_price_touches` 中在同一秒内被写入了重复的触达快照记录。

### 2. 根因剖析
云端配置了每 10 秒执行一次的定时任务，而前端用户在盘中也会手动点击“刷新行情”。当定时任务与手动刷新在同一瞬间（微秒级）并发读取到标的越过价格线时，两边均未读到 `buyTriggered: true`，随后各自执行无条件 `update` 并分别触发了推送接口，形成了典型的并发竞争（Race Condition）。

### 3. 防护与开发铁律
1. **【铁律：Serverless 关键写操作必须使用 CAS 乐观锁原子抢占】**：
   状态变更与提醒下发严禁直接 `doc(id).update(...)`，必须使用数据库条件原子更新：
   `db.collection('ths_watchlist').where({ _id: w._id, buyTriggered: _.neq(true) }).update(...)`；
2. **【铁律：严格检查更新影响行数】**：
   只有当更新受影响行数严格等于 1 时，当前线程才获准执行“写入 touch 快照”与“调用微信推送接口”；其余并发失败线程仅执行静默行情同步，绝不重复发信。

## 📌 案例 8：跨市场标的跨日判定受北京时间污染（2026-09-03）

### 1. 现象描述
美股常规交易时段横跨北京时间午夜 0:00。在系统运行到北京时间凌晨 0 点整时，美股仍处于美东白天正常交易时段中，但系统却判定“已跨日”，将美股日内防抖与成交状态截断重置。

### 2. 根因剖析
代码在统一计算 `marketToday` 时，全局调用了 `beijingParts(nowMs).compactDate`。以国内北京时区裁决美股交易所的交易日历，违背了金融市场的独立时区客观规律。

### 3. 防护与开发铁律
1. **【铁律：双时区独立日历裁决】**：
   中美市场日历与跨日裁决必须分流：
   - A 股与中国 ETF：严格采用 `beijingParts`（`Asia/Shanghai`）；
   - 美股与美股 ETF：严格采用 `usNewYorkParts`（`America/New_York`，自动自适应夏令时与冬令时）；
2. 跨日与日内状态判定必须以标的自身的交易所本土时间为准，杜绝任何跨时区污染。

## 📌 案例 9：持久化达成标记生命周期未闭环导致 UI 紫色边框常驻（2026-09-03）

### 1. 现象描述
标的“有色金属ETF南方”昨天曾跌破过买入价，今天价格已反弹上涨至正常波动区间（既未达买入价，也未达卖出价），但卡片依然顶着醒目的 2px 紫色粗边框与“目标已达成”徽章，且常驻置顶，严重误导用户。

### 2. 根因剖析
系统在昨天触发提醒时，向数据库写入了持久化字段 `buyAchievedAt`；当今天价格反弹离开目标区间后，状态机虽然将 `buyTriggered` 重置为 `false`，但未同步将 `buyAchievedAt` 清空复位；前端代码又单凭 `w.buyAchievedAt` 是否存在盲目添加 `.card.done` 样式，导致卡片被永久锁死在达成高亮态。

### 3. 防护与开发铁律
1. **【铁律：脱离区间自动复位达成生命周期】**：
   重新武装（rearm）必须是完整闭环：当标的价格离开目标区间后，不仅要释放触发锁，必须同步将 `buyAchievedAt / sellAchievedAt` 复位为 `null`；
2. **【铁律：UI 告警高亮必须以当前实时价格为最高准则】**：
   前端只有在当前现价真正满足条件（现价 $\le$ 买入价显示绿色，现价 $\ge$ 卖出价显示红色）时才展现高亮置顶；处于正常波动区间的标的一律回归干净清爽的“监控中”底色。

## 📌 案例 10：上游金融 API 接口瞬时高并发网关拦截与平滑节流（2026-09-03）

### 1. 现象描述
监控列表中录入了 16 只中国 ETF，系统在全量巡检时，状态栏频繁提示“行情状态：部分异常”，抓取日志发现多只 ETF 报错 `request limit exceeded`。

### 2. 根因剖析
同花顺开放平台的 ETF 快照接口不支持逗号批量查询，只能逐只单独发起 HTTP 请求。云函数在毫秒级时间内连续密集发起 16 次请求，瞬时并发 QPS 触发了同花顺 API 网关的防刷拦截策略。

### 3. 防护与开发铁律
1. **【铁律：单标的串行接口必须加入节流微间歇】**：
   对于必须逐只请求的上游接口，在循环中强制引入 `150ms` 的请求微间歇，平滑并发流量；
2. **【铁律：上游限流引入自动指数退避重试】**：
   捕获到 `limit exceeded` 错误时，系统自动休眠 `350ms` 后原地重试 1 次，将全量标的获取成功率提升至 100%，彻底消灭因上游网关拦截导致的状态告警。
